# Epic: Peak readiness

Phase 6 · repository `shop-web` · areas `contract-client`, `infra`, `catalog`, `cart`, `auth`,
`e2e` · tracking issue: _created with this PR_

## Goal

Make the storefront behave on 12.12 as the plan's Phase 6 row asks: optional holes (recommendations
on Home, member price on the PDP) can be switched off at runtime by the feature flags shop-api
serves, without errors and without leaving the static shell; the header badge renders the cart
count instantly from a non-httpOnly `cart_count` hint cookie, also when the cart call fails;
Lighthouse budgets guard Home, PDP and Cart; and load-test journeys measure shell TTFB and the cart
hole against `make demo-peak`. Plan § Frontend plan, Phase 6: "Lighthouse budgets pass; flags switch
holes off without errors." Backed by shop-api's Peak readiness epic (Phase 6), contract `1.5.0`.

## Scope

In scope:

- Pin `@shop/api-contract` `1.5.0` (the release of shop-api's Peak readiness epic), regenerate
  types, MSW handlers and fixtures for `GET /api/flags` with "all on" and "all off" scenarios.
- A server-side flags reader in `src/lib/flags/` with a budget and safe defaults.
- The recommendations and member-price holes honour their flags.
- The `cart_count` hint cookie: written by the cart feature, read by the header badge, cleared on
  logout.
- Lighthouse CI with budgets for Home, PDP and Cart (`make lighthouse`), and a nightly workflow
  that opens an issue on regression.
- Playwright journeys for flags off and for the badge hint when the summary call fails.
- k6 load-test journeys against the web server and the peak stack (`make load-journeys`).

Out of scope: the PDP delivery-date estimate (`ProductServiceInfo` mentions it, but the PDP artboard
shows only static service rows and there is no contract operation; open question 2); flags for
holes other than recommendations and member price (similar products are cached for hours and cost
nothing at peak); a waiting room; a shared cache handler for several Next.js replicas (open question
3); changes to `src/proxy.ts`; any backend work.

## Decisions

See `docs/handoff/technical-notes.md` § 3 (caching rules and the hint cookies: "A non-httpOnly hint
cookie (`logged_in=1`, `cart_count=N`, nothing sensitive) lets the client render the right skeleton
instantly") and § 7 (feature flags switch optional holes off under load; every hole has a 150–300
ms budget and a fallback). Read `node_modules/next/dist/docs/` for `'use cache'`, `cacheLife` with
custom profiles and `connection()` before writing the flags reader (do not rely on memory).

| Topic                | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flags source         | shop-api's `GET /api/flags` (contract `1.5.0`): `{ recommendations, memberPrice, onlinePayment }`, switched at runtime by the operator (`make flag` in shop-api). Flags are shared data, not user data, so they may be cached in Next.js.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Flags reader         | `src/lib/flags/flags.server.ts` (`server-only`): `getFlags()` with `'use cache'`, `cacheLife({ stale: 5, revalidate: 5, expire: 60 })` and `cacheTag("flags")`, fetching over the internal network with `serverApi("core", { budgetMs: 100 })`. On a timeout or error it returns the defaults (all on) and logs once per failure; it never throws. Features import it from `lib`, so no feature imports another. Budget: a hole awaits `getFlags()` first (usually a 5 s cache hit) and calls its data endpoint only when the flag is on, with the remaining budget (`250 ms − time spent on getFlags()`), so nothing is called when a flag is off and the hole stays inside its 250 ms budget (owner decision, option C on #134). A component test with a slow flags reader (100 ms) and a slow data call checks the hole still resolves within its budget.                                                                                                                                                                                                                                                                                                                                                         |
| Where flags are read | Only inside the existing dynamic holes (under their `<Suspense>`), never in the static shell or the root layout, so prerendered shells do not change when a flag flips. A flag switched off takes effect within about 5 s plus the cache revalidation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Recommendations off  | `RecommendationsSection` reads `recommendations`; off → it renders nothing and does not call `/api/recommendations` (the artboard's "timeout → ẩn" behaviour, so the page looks as it does after a timeout).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Member price off     | `MemberPrice` reads `memberPrice`; off → it renders nothing, does not call `/api/products/{slug}/member-price` from the server, and passes nothing to the client fallback, so the browser does not call it either. The login prompt for guests is also hidden (it advertises the member price).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `onlinePayment`      | Not read by shop-web: shop-api already reports `EWALLET` and `CARD` with `available: false`, which the checkout page renders as disabled ("Tạm thời không khả dụng", Checkout epic).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `cart_count` cookie  | `src/lib/hints/cart-count.ts`: `writeCartCount(n)` sets `cart_count=<n>; Path=/; Max-Age=2592000; SameSite=Lax` (`Secure` on https), `readCartCount()` parses it (integer 0–999, anything else → none), `clearCartCount()`. Set by the browser, not by shop-api, so the contract does not change. The value is a hint only: never used for logic, never sent anywhere on purpose.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Writing the hint     | The cart feature writes it after every successful `cartQueries.summary()` or `cartQueries.mine()` result (`itemCount`) and after every successful cart mutation and the guest merge, in one place (a `QueryCache`/`MutationCache` subscription in the cart feature's client entry, or the query functions), so all paths agree. A server-rendered cart hole never writes it (Server Components cannot set cookies).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Badge                | `CartBadge` shows `data.itemCount` when the summary query has data; while it is pending or after an error it shows `readCartCount()` (read after hydration with `useSyncExternalStore`, server snapshot "no hint", so the static shell is unchanged and there is no hydration mismatch). The hint is never put into the query cache (`placeholderData`/`initialData`), so server data stays in TanStack Query only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Logout               | The auth feature's logout clears `cart_count` together with `logged_in` (`clearCartCount()` from `lib`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Lighthouse           | `@lhci/cli` (dev dependency) with `lighthouserc.json` and `lighthouse-budgets.json`, run by `make lighthouse` against the production build with the stub gateway (`e2e/support/stub-gateway.ts`, as `make e2e`), mobile preset, 3 runs per URL, median. URLs: `/`, the first flash-sale PDP, `/cart`. Assertions (owner decision, open question 1): measured first. The Lighthouse task runs `make lighthouse` on `main` before it sets any assertion, records the medians in the PR, and sets each budget at the measured value plus 10 % for LCP, CLS, TBT, script transfer and total transfer per page; the performance and accessibility scores at the measured value minus 0.05, never below 0.8 for performance and 0.9 for accessibility when the measured score allows it; a score already below its floor + 0.05 gets the measured value − 0.05 as its budget and is reported to the owner, so `make lighthouse` passes on `main`. Reports are written to `.lighthouseci/` (git-ignored).                                                                                                                                                                                                                   |
| Nightly Lighthouse   | `.github/workflows/lighthouse-nightly.yml` runs `make lighthouse` on a schedule and `workflow_dispatch`, uploads the reports, and on a failed assertion opens or updates an issue labelled `bug` + `area:infra` with the failing metrics. Protected path: that task carries `infra-change` and needs the owner's `human-approved`. PR CI does not run Lighthouse (too noisy on shared runners).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Flag journeys        | Playwright, desktop and phone with axe: Home with `recommendations` off has no recommendations section and no console errors; PDP with `memberPrice` off has no member price row and sends no member-price request; with both on, today's journeys still pass. The stub gateway needs a `/api/flags` route with a scenario switch, so that task edits an existing `e2e/support` file and carries `infra-change`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Badge journey        | Playwright: after adding to cart the badge shows N; on reload with the stub's summary answering 503, the badge still shows N from the hint; after logout no badge. Same task as the flag journeys (both need stub-gateway changes).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Load-test journeys   | `perf/k6/journeys.js`, run by `make load-journeys` with the `grafana/k6` Docker image against `make demo` of shop-web and `make demo-peak` of shop-api: 30 VUs, 2 minutes, a journey Home → PDP → add to cart (through `/api/*`) → `/cart`. Thresholds: Home and PDP TTFB p95 < 200 ms, `/cart` TTFB p95 < 400 ms (250 ms hole budget plus rendering), error rate < 1 %, also during shop-api's toxiproxy phase. The web server's server-rendered cart hole calls `cart-service` directly (`CART_INTERNAL_URL`, `src/lib/api/server.ts`), not through the gateway, so `make load-journeys` starts shop-web with `CART_INTERNAL_URL` pointing at shop-api's second toxiproxy proxy (`cart-service-web`, host :18083); only then does the toxic slow the hole and make it fall back to the client within its 250 ms budget. During the toxic phase the browser's cart reads through `/api/*` answer 503 `SERVICE_UNAVAILABLE` by design (gateway fallback): the script declares 503 an expected status for cart reads in that phase (`http.expectedStatuses`, tagged), and the error-rate threshold applies to every other request. A `/cart` page response is always 200 (the hole falls back, the page never fails). |
| Sensitive paths      | No task changes `src/proxy.ts` or `src/features/auth/**` beyond the logout hint clearing (reviewer security checklist). Protected paths: the e2e stub change and the nightly workflow (`infra-change`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Risks and mitigations

| Risk                                                                 | Mitigation                                                                                                                                               |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The flags call becomes a new hot dependency                          | Cached for 5 s per server instance, 100 ms budget, defaults on failure; it is read only inside holes that already stream.                                |
| A flag read sneaks into the static shell and makes a page dynamic    | `layout-static-shell.test.ts` and the build's prerender output stay green; the catalog task adds a test that `page.tsx` files do not import `lib/flags`. |
| The hint shows a wrong count (another tab, another device)           | It is shown only until the summary query answers, and rewritten on every successful read; it never drives logic.                                         |
| Hydration mismatch from reading a cookie during render               | `useSyncExternalStore` with a server snapshot of "no hint"; a component test renders on the server and hydrates.                                         |
| Lighthouse scores vary between runs and runners                      | Median of 3 runs, thresholds with headroom, nightly issue instead of a PR gate.                                                                          |
| Load journeys depend on the shop-api peak stack                      | Task 10 depends on shop-api's peak profile and k6 peak tasks; the script reads `WEB_URL` and `GATEWAY_URL` so it also runs against `make demo`.          |
| `make lighthouse` and k6 cannot run in cloud sessions without Docker | Lighthouse runs with Chromium from Playwright; k6 runs in CI or locally; workers wait with `checks-wait`.                                                |

## Open questions for the owner

1. **Budget values.** Decided by the owner: measure the current pages first and set budgets at the
   measured values plus 10 % (Lighthouse row).
2. **Delivery-date estimate.** The Home + PDP epic deferred a feature-flagged delivery-date hole to
   Phase 6, but the PDP artboard has no such element and there is no contract operation. Proposed:
   out of scope until an artboard and an operation exist. Alternative: a contract task in shop-api
   and a flagged hole in this epic.
3. **Several Next.js replicas.** `revalidateTag` reaches only the instance that received the webhook
   (Home + PDP epic risk). Proposed: out of scope; the demo runs one instance and the cache lifetimes
   bound staleness. Alternative: a shared cache handler (Redis) for `'use cache'` as an extra
   `infra` task.
